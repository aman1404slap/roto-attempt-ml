# Handover — the zero-margin plan, what to report back, and what comes after

Audience: Lokesh. Context: v1.1 reviewed, four new rungs in flight (`window_aligned`,
`window_temporal_aligned`, `affine_crop`, `affine_crop_aligned`).

## 1. The principle: split the error, then kill the half we control

"No pixel error" is the right ambition and the wrong single number. Split every pixel of
disagreement into two buckets and treat them completely differently:

**Bucket A — pipeline error.** Conversions, alignment, scoring, rendering conventions,
interpolation. This bucket must be **exactly zero**, provable, with a test pinning each item.
Any error here silently caps the model and poisons every experiment comparison.

**Bucket B — model error.** The network's own geometry/timing error. This is minimized, never
assumed zero, and — because this is VFX — measured by the **worst frame**, not the average. A
shot with 190 perfect frames and one bad one is a rejected shot. Every report below therefore
carries min/p95/max alongside the mean.

The exit condition for this phase: Bucket A provably zero, Bucket B characterized per layer
with worst-case numbers and a known run-to-run noise floor.

## 4. Decision tree once the numbers land

- **Aligned window helps** (jitter ↓ and point px not worse) → adopt into the default config;
  re-sweep the keyframe operating point (the old sweep was tuned to the old noise floor).
  **Doesn't help** → the window idea is honestly closed; jitter work moves to prediction-space
  (predict per-frame deltas from the previous prediction, i.e. a cheap recurrent refinement) —
  design note first, not code.
- **Crop-space transform head works** (rendered-with-predicted-motion within ~0.02 of
  teacher-forced) → schedule the first de-teacher-forcing rung: reconstruction using predicted
  transforms end to end. **Doesn't** → give the head its own small decoder depth before giving
  up; motion is the hardest single-frame quantity.
- Either way next: **dataset rebuild** with the measured-correct conventions
  (`fill_open_zero_width=False`, hairline stroke gain with 1 px floor, `duplicate` endpoints),
  more layers/shots from the drop, **held-out-shot split** defined at build time — then one
  re-baseline, which becomes the reference for everything after.
- Then the **key-timing head**: per-frame, per-shape probability of "artist keys here",
  supervised by the artist's actual keys (currently unused as a training signal — the likeliest
  route off the flat 0.36–0.41 key F1), used to bias the DP's local tolerance.

## 5. GPU: local vs AWS — the honest answer

**Stay local through this ladder.** The workload today is a 3M-param model, ~500 MB of
tensors, 40k steps in tens of minutes on the 5050; attention at S=1,036 costs 0.19 GB. AWS now
adds setup cost and zero capability.

**Move to managed GPU at the dataset-rebuild milestone**, and for two reasons in this order:

1. **Data governance, not compute.** The training data is client production material; the
   moment the dataset grows past the sample drop, it should live on approved infrastructure,
   not a personal machine. That argument arrives with the archive subset regardless of speed.
   Confirm with Jon whether that means company AWS, on-prem, or a specific approved account —
   don't spin up a personal instance for client data.
2. **Parallelism.** The ladder methodology is one-change-per-run; more layers × more rungs ×
   seed repeats multiplies runs, and parallel single-GPU instances is where cloud actually pays.

Right-size when it happens: one A10G/L4 class card per run (g5.xlarge / g6.xlarge), spot
instances, dataset synced once to the instance, checkpoints and `results/*.json` synced back —
the existing config/logging discipline already makes runs reproducible, keep it. No multi-GPU
until the model itself grows (dynamic queries / temporal encoder), which is a v2-scale
question, not a now question.

## 6. One-line summary

Prove every pixel we control is exact (ledger green, two new tests, noise floor measured),
report model error worst-case per layer on the four in-flight rungs plus the constrained key
sweep, price the predicted-transform gap — and move to approved cloud GPUs when the dataset
grows, for governance and parallel rungs, not for speed.
